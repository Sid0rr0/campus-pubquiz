# Milestone 4 Plan — Concurrent Game Sessions

## Problem

The backend can only run one active `GameSession` at a time per process.
`GameStateService` is a NestJS singleton holding scalar fields (`progress`,
`seededGame`, `teams`, `leaderboard`, `connectedTeamSockets`) for exactly one
game, and `GameGateway` broadcasts to three *global* Socket.IO rooms
(`display`, `admin`, `players`) with no session scoping. Selecting a new quiz
(`selectQuiz`) replaces that single state wholesale — there is no way to run
two quiz nights (or two rooms of the same quiz night) from one backend
instance at once.

## What's already there (grounding, not assumptions)

Read `game.gateway.ts`, `game-state.service.ts`, `game-session.entity.ts`,
`seed.service.ts`, `team.service.ts` before writing this plan. The
persistence/domain layer is already almost entirely session-scoped:

- `GameSession.joinCode` is already a unique-per-session column
  (`db/entities/game-session.entity.ts`), generated by
  `SeedService.createSession()`.
- `TeamService.join()` already validates a supplied `joinCode` against a
  specific `gameSessionId` (`InvalidJoinCodeError`) — team join is not
  globally scoped, it's per-session already.
- `AnswerService`, `BonusService`, `GameProgressRepository` all take
  `gameSessionId` as an explicit parameter on every method — none of them
  hold session state themselves.

So the gap is narrower than "add multi-tenancy everywhere": it's specifically
the **real-time layer** — `GameStateService`'s scalar in-memory fields, the
gateway's ungrouped rooms, and its single `questionLockTimer` instance field
— plus the **admin UX** for creating/picking a session, since today there is
exactly one implicit active game.

## Goal

Run N concurrent `GameSession`s in one backend process, each addressed by
its `joinCode`. `/display`, `/admin`, `/play` all take the code via a
`?code=` query param; Socket.IO rooms and in-memory state are keyed by it.
Single-session behavior (today's UX) still works when there's only one
session — this is additive, not a rewrite of the state machine itself.

## Phases

| # | Phase | Summary |
|---|---|---|
| 1 | Shared types | `shared/types`: add `code` to the socket handshake contract, a `sessionRoom(code, role)` helper so the `display:${code}` naming convention lives in one place, and `CreateSessionPayload`/`ActiveSessionSummary` types for the new session-lifecycle actions. |
| 2 | `GameStateService` → per-session state | Replace scalar fields (`progress`, `seededGame`, `teams`, `leaderboard`, `connectedTeamSockets`, `answeredTeamIdsByQuestion`, `leaderboardRevealCount`) with a `Map<joinCode, SessionState>`. Every public method (`getSnapshot`, `applyAction`, `selectQuiz`, `setTeams`, etc.) takes `joinCode` as its first argument. `selectQuiz` is replaced by `createSession(quizId)`, which allocates a **new** joinCode/state entry instead of overwriting the current one. |
| 3 | `GameGateway` room scoping | Handshake query gains `code` alongside `role`; reject the connection if `code` doesn't resolve to a known session. Clients join `${role}:${code}` instead of bare `role`. `broadcastState` targets that session's three rooms. `questionLockTimer` becomes `Map<joinCode, NodeJS.Timeout>`; `onModuleDestroy` clears all of them. `client.data` stores `joinCode` at connect time so `handleDisconnect` can update the right session's roster. |
| 4 | Session lifecycle admin surface | `POST /sessions` (create: pick a quiz → get a joinCode) and `GET /sessions` (list currently-running sessions, admin-guarded, mirrors the `import.controller.ts` admin-REST precedent) so an admin can start a new game or attach to one already running. Decide + implement eviction of ended/idle session state from the in-memory map (see open question below). |
| 5 | Frontend wiring | Thread `?code=` through `/display`, `/admin`, `/play`. Admin gets a session picker/creation screen before landing on a specific session's controls (replaces today's implicit single game). Socket-connecting hook(s) pass `code` into the handshake query. Any join-link/QR code generation includes `?code=`. |
| 6 | Verification | New tests proving two concurrent sessions progress independently (state, rosters, question-lock timers) with zero cross-talk — a client in session A's admin room must never receive session B's broadcasts. Full `pnpm test` / `pnpm lint` / `pnpm build` across workspaces. |

## Risks

- **Phase 2 is the highest-regression-risk phase** — it touches nearly every
  method on `GameStateService` and every call site in `GameGateway`. Do it
  with TDD, one method at a time, keeping the existing single-session test
  suite green throughout rather than batching the whole rewrite.
- **Timer correctness** — per-session question-lock timers must not leak
  (process restart, session end) or fire against the wrong session.
- **Reconnection** — reconnect is called out in `CLAUDE.md` as a core
  feature (phones sleep, networks drop). The team's `localStorage` token
  needs to carry (or be looked up together with) the session's joinCode, or
  reconnecting after a backend restart with multiple past sessions could
  reattach a team to the wrong game.
- **Memory growth** — an in-memory `Map` keyed by joinCode needs an eviction
  policy or a long-running process accumulates state for every quiz night
  it's ever run.

## Open questions (need a decision before/at Phase 4–5)

1. **Session creation surface**: REST (`POST /sessions`, matches the
   `import.controller.ts` admin-REST pattern) or a new socket admin action
   (matches how `SELECT_QUIZ` works today)?
2. **Eviction policy**: when does a session's in-memory state get dropped —
   fixed idle timeout after `ended`, explicit admin "close session" action,
   or both?
3. **Admin scope**: can one logged-in admin/moderator see and switch between
   *all* running sessions, or should each session have its own admin login
   scope? (Affects the Phase 4/5 admin picker UI.)

## Out of scope for this milestone

- Horizontal scaling / Redis adapter — still one backend process, just
  multi-tenant within it. Matches the existing accepted tradeoff in
  `CLAUDE.md` ("One backend instance only... At pub-quiz scale this is
  intentional and correct").
